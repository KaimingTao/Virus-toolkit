# Handling `429 Too Many Requests`

`literature_scripts/pubmed_search.py` already contains the main patterns this repo uses to reduce or recover from rate limiting. The relevant pieces are:

## What `pubmed_search.py` does

### 1. It slows requests down on purpose

It defines:

```python
REQUEST_DELAY_SECONDS = 0.34
```

and then sleeps after API calls, for example after `count_pubmed_hits`, `collect_pubmed_history`, and each fetched batch.

Conclusion:
- Do not send requests back-to-back at full speed.
- Add a fixed delay between calls.
- If `429` still happens, increase the delay.

### 2. It caches successful responses on disk

It stores API responses under `pubmed_search_cache/` using a hash of normalized request parameters:

- `normalize_cache_params(...)`
- `build_cache_key(...)`
- `load_cache_entry(...)`
- `save_cache_entry(...)`

Conclusion:
- Cache responses locally.
- If the same request is repeated, reuse cached data instead of calling the API again.
- This is one of the easiest ways to cut request volume and avoid `429`.

### 3. It retries failed requests with backoff

In `request_xml(...)`, it retries up to 3 times:

```python
for attempt in range(1, retries + 1):
```

and waits longer on each retry:

```python
time.sleep(attempt)
```

Conclusion:
- Do not fail immediately on transient HTTP errors.
- Retry a small number of times.
- Wait longer on later retries.

### 4. It includes identifying contact information

It passes:

- `email`
- `api_key` for NCBI when available

through `build_params(...)`.

Conclusion:
- Identify the client when the API supports it.
- For Crossref specifically, use the polite pool with `mailto` and a descriptive `User-Agent`.

## Practical resolution for similar `429` issues

For scripts in this repo, the same approach should be applied in this order:

1. Add or increase request delay.
2. Add local response caching keyed by request parameters.
3. Add bounded retry with incremental backoff.
4. Send identifying client information expected by the API.
5. Reduce duplicate requests by memoizing repeated lookups inside one run.

## How this applies here

### `fetch_pmc_files.py`

Current state:
- Has a fixed delay.
- Does not have retry logic.
- Does not have persistent cache.

So if it gets `429`, the next changes should be:
- add request retry with backoff around `request_json(...)` and `request_xml(...)`
- add on-disk cache for PMCID lookup responses and OA-link responses
- increase `REQUEST_DELAY_SECONDS` if needed

### `crossref_search.py`

Current state:
- Already has local cache
- Already uses `mailto`
- Already sets `User-Agent`
- Has a small fixed delay
- Does not yet retry on `429`

So if it gets `429`, the next changes should be:
- add retry with backoff in `request_json(...)`
- possibly increase `REQUEST_DELAY_SECONDS`
- keep cache enabled and avoid re-running uncached broad searches unnecessarily

## Bottom line

The repo pattern from `pubmed_search.py` is:

- throttle
- cache
- retry with backoff
- identify the client

That is the standard fix path for `429` in the other literature scripts as well.
